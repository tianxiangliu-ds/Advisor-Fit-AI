# Agent Harness 架构

> 这份文档讲的是**这个项目作为一件 Agent 工程作品**长什么样：
> 有哪些模块、循环怎么转、工具怎么管、钱和次数怎么控、证据怎么接地、现在到哪一步了。
>
> 面向普通用户的使用说明在 [README](../README.md)。

---

## 一句话

**AdvisorFit AI = 一个面向"导师研究匹配"这个具体任务的自研轻量 Agent Harness + 跑在它上面的一个 Agent + 一层给人用的界面。**

任务本身是：给一份学生简历和一位导师，自己决定去查什么、怎么确认这个导师是谁、
他到底研究什么，最后给出一份**每句话都能点开看来源**的匹配分析。

---

## 为什么需要一个 Harness，而不是把 API 拼成流水线

流水线的写法是：`解析 CV → 检索 → 消歧 → 分析 → 生成邮件`，每一步写死。
在这个任务上它会立刻撞墙，因为**下一步查什么取决于上一步查到了什么**：

- 按"姓名 + 学校"查不到 → 该去掉学校再试，还是改用代表论文标题兜底？
- 查回来 25 篇但机构五花八门 → 是接着扩搜，还是先问用户"这些是不是同名的人"？
- 论文一篇都查不到 → 该不该去他的个人主页看看他到底写的是什么方向？

这些判断需要模型来做，而**一旦让模型做判断，就必须有人管住它**：它可能陷入循环、
可能把额度烧光、可能调一个不存在的工具、可能给出无法追溯的结论。

Harness 就是干这个的：**给模型自由，同时把自由关在笼子里。**

## 模块总览

| 模块 | 位置 | 职责 | 状态 |
|---|---|---|---|
| **Model**（模型层） | `llm/provider.py` | 多供应商可切：DeepSeek / OpenAI / Anthropic / Ollama；统一结构化输出；不可用时降级 | ✅ |
| **Prompt**（提示词） | `llm/prompts.py` | 提示词登记表，带版本号；10 条提示词集中管理，不在业务代码里散落 | ✅ |
| **Tool**（工具层） | `harness/tools.py`、`agents/tools.py` | 工具契约与注册表；声明与实现分离；装配时校验一一对应 | ✅ |
| **Loop**（循环层） | `harness/loop.py` | LLM 决策 → 执行工具 → 结果回传，直到结束 / 请求确认 / 预算耗尽 | ✅ |
| **Budget**（预算闸门） | `harness/budget.py` | 按维度记账（步数/token/外部请求/单来源/墙钟），超限优雅降级而非抛错 | ✅ |
| **Trace**（轨迹） | `harness/trace.py` | 每一步都可追溯：调了什么、参数摘要、耗时、成功失败、这次给了哪些工具 | ✅ |
| **Context**（上下文） | — | 上下文窗口的显式组装与裁剪策略 | ⚠️ 目前隐式（由各调用点拼 payload） |
| **State**（状态） | — | 跨轮/跨会话的运行状态机 | ⚠️ 目前靠 Streamlit session + SQLite artifacts |
| **Workflow**（工作流） | — | 显式的工作流定义（阶段、门控、回退） | ⚠️ 目前写在 `agents/research.py` 的控制流里 |

> 最后三行是**诚实的缺口**，不是已完成项。现在的抽象程度够支撑当前任务，
> 但离"可复用、可声明式编排的 Workflow"还有距离。这是下一阶段的主要工作。

## Agent 循环怎么转

```
        ┌──────────────────────────────────────────────┐
        │  1. 预算闸门检查：任何一维触顶就停止并记录降级原因  │
        └───────────────────────┬──────────────────────┘
                                │
                    ┌───────────▼───────────┐
                    │ 2. 把「任务 + 工具清单  │
                    │    + 历史步骤」交给 LLM │
                    └───────────┬───────────┘
                                │  返回结构化决策
        ┌───────────────────────┼───────────────────────┐
        │                       │                       │
   action=tool             action=confirm           action=done
        │                       │                       │
   执行工具（失败也回传）    未授权 → 暂停并问用户      记录结论并返回
        │                  已授权 → 继续
        └──────────► 结果追加进历史，回到 1 ◄──────────┘
```

几个刻意的设计选择：

- **工具契约在循环里被真正执行**，不是"声明了好看"：单轮限流、超时、重试都按
  `ToolSpec` 的声明生效。这一点单独强调，是因为曾经出现过"声明了重试但循环里
  只是 `fn(**args)`"的情况——那比不写更危险，读代码的人会以为网络抖动已经被
  兜住了，实际上整轮检索就此丢掉。
  - **重试**：失败后按 `max_attempts` 与线性退避再试，重试次数写进轨迹；
    **每次尝试都计入外部请求预算**，重试不能白花额度。
  - **限流**：`rate_limit_per_run` 是**按工具**计的，超额时把错误回传给模型
    （而不是静默丢弃），模型可以换一个工具继续。
  - **超时**：工具在后台线程里跑，超过 `timeout_seconds` 就判超时并继续循环。
    一个卡住的工具不能拖死整轮——这是上线后最难受的一类故障。
- **工具失败不中断循环。** 异常被包成 `{"error": ...}` 回传给模型，让它自己决定换招。
- **确认门控是"暂停"而不是"报错"。** 模型可以主动说"这里有歧义，我不往下走了"，
  界面把它变成三个按钮（确认继续 / 去掉学校重试 / 全部保留我手动核对）。
- **预算超限是降级不是崩溃。** 记下 `degraded_reason`，保留已拿到的证据，
  在结论里标注来源不可用。
- **纯规则兜底路径。** 没有配 LLM 时走 `_research_without_llm`，核心流程仍然可用。

## 工具契约

工具规格集中在 `agents/tools.py` 声明，实现可以注入。**装配时强校验**：
声明了没实现、实现了没声明，都直接报错——宁可启动时炸，也不让模型看到一个
"存在但调不通"的工具。

| 工具 | 权限 | 单轮上限 | 超时 / 重试 | 缓存 | 干什么 |
|---|---|---|---|---|---|
| `search_by_author` | network | 4 | 20s / 2 次 | 24h | 按姓名+学校在多个学术库检索候选论文 |
| `search_by_title` | network | 6 | 20s / 2 次 | 24h | 按论文标题检索（作者名查不到时兜底） |
| `fetch_professor_homepage` | network | 2 | 20s / 2 次 | 7d | 打开导师个人主页，抽取职称/院系/邮箱/研究方向 |
| `check_paper_affiliations` | read | — | 5s / 不重试 | — | 核对当前候选论文机构与目标学校是否一致 |

**权限模型**：`network` 工具会发外部请求，受预算闸门统计；`read` 工具只读本次运行
已有的数据，不消耗外部额度。这个区分不是道德标签，是**真的会改变记账行为**。

上表的每一列都由循环强制执行（见上一节）。`read` 类工具刻意不重试——只读操作
重试没意义，而有副作用的操作重试更危险，所以默认 `max_attempts=1`，要重试必须
显式声明。

工具是模型能做的事的**全部边界**——它不能读取任意文件、不能访问任意 URL、
只能通过这 4 个工具接触外部世界。

## 预算闸门

上限数值定义在 `harness/budget.py`，与 `CLAUDE.md` 保持一致：

| 维度 | 上限 |
|---|---|
| 循环步数 | 5 步 |
| LLM 调用 | 15 次 |
| token | 150k 输入 / 30k 输出 |
| 外部请求 | 25 次；同一来源 ≤ 8 次 |
| 墙钟时间 | 120 秒 |

`exceeded()` 返回**第一个触顶的资源码**（顺序固定，便于测试与复现），
循环据此停止并把原因写进轨迹。

## 运行轨迹：让 Agent 可见

轨迹是这套设计里最容易被忽略、但对使用者最重要的一环。

**为什么重要**：Agent 的"自主性"如果不可见，用户只看得到结论，无法判断它是
**查出来的**还是**编出来的**。

轨迹记录三类信息：

1. **这次给了模型哪些工具**（名称/说明/参数 schema/权限）——只记"实际调了什么"
   看不出它当时有哪些选择，也就无法复盘"它为什么没选另一个工具"；
2. **每一步**：序号、类型（模型决策/工具调用/人工确认/异常/结束）、工具名、
   参数摘要、状态、耗时、结果摘要；
3. **资源消耗**：步数、工具调用数、耗时、token、外部请求数，以及降级原因。

轨迹落库（SQLite artifacts），并在「论文核验」页与「研究档案」回看时展示，
可导出 JSON。参数与结果**只存摘要**——整篇论文列表和 CV 原文不进轨迹、不进数据库。

## 证据接地（Evidence Grounding）

这一层是这个项目区别于"套个 LLM 外壳"的地方：

- **三态分离**：所有结论分 `FACT / INFERRED / UNKNOWN`，没有证据就写"未知"，
  不补全、不猜测。
- **字段级来源**：每个字段（职称/邮箱/院系/研究方向）都记来源与抓取时间，
  见 `models/provenance.py`。手动填写与官网抓取**不混为一谈**。
- **Claim–Evidence 映射**：进入报告的每条陈述都要能落到具体证据上，
  见 `llm/claims.py`、`validation/claims.py`。
- **作者消歧**：同名作者是这个领域的头号噪声。按机构、邮箱域名、院系、论文机构、
  主题连续性等多锚点打分，输出 `CONFIRMED / REVIEW_REQUIRED / REJECTED`
  （`analysis/identity.py`），拿不准就请人确认。
- **多源检索 + 学科分流**：检索源是**配置而非代码**（`providers/sources.py`
  可被 `config/sources.json` 覆盖）。默认 7 个源，主干免费免 Key：

  | 来源 | 覆盖 | 默认 |
  |---|---|---|
  | OpenAlex | 全学科 | 开 |
  | Crossref | DOI 元数据 | 开 |
  | Europe PMC | 生物医学 | 开 |
  | arXiv | 物理/计算机/化学/工程/经济 | 开 |
  | DBLP | 计算机 | 关（默认用 OpenAlex 即可） |
  | 万方 | 中文 | 需 Key，缺 Key 跳过并说明原因 |
  | AMiner | 中文与学者画像 | 关（按次计费） |

- **按姓名检索必须核对**：学术库的"按姓名搜"普遍是模糊匹配，捞回来的结果一律
  过 `providers/author_match.py` 的严格核对；机构对不上时宁可退回候选池，
  也不许按"论文数最多"随便认一个同名档案。

## 降级策略

一个只在理想条件下能跑的 Agent 是没有用的。当前的降级路径：

| 情况 | 行为 |
|---|---|
| 没配 LLM Key | 走纯规则路径，核心流程仍可用（`_research_without_llm`） |
| LLM 调用失败 | 记录 `skipped` 步骤，停止循环，返回已有候选 |
| 某个学术库不可用 | 跳过该来源并在结果里标注，不让主流程失败 |
| 网页抓不到 / JS 渲染 | 退回规则提取；仍拿不到就标 `UNKNOWN`，不编 |
| 同名作者拿不准 | 请求人工确认，不擅自认定归属 |
| 预算触顶 | 记录降级原因，保留已得证据，标注来源不可用 |

## 评测

四个维度各有一组可量化指标，统一入口是 `scripts/run_all_evals.py`：

| 维度 | 指标 | 门线 |
|---|---|---|
| 实体消歧准确性 | 规则基线 precision / recall / F1 | **只卡召回 ≥ 90%**（见下） |
| Evidence 覆盖率 | Claim–Evidence 判定一致率、无证据声明被拦下数 | 一致率 100% |
| 匹配一致性 | 结果确定性、单调性 | 两项均须 1.0 |
| LLM 输出可靠性 | 提示词登记数、可用率；有 Key 时加跑真实模型消歧 | 可用率 100% |

**为什么规则基线只卡召回**：规则路径不排除任何论文，只把机构对不上的标成
"需人工复核"，所以它的 precision 恰好等于金标里的正例比例——那是**下限而不是
成绩**。门线压在 precision 上会永远失败。提精度是 LLM 与人工确认的活，
规则基线的职责是"别漏人"。

**为什么单调性看缺口而不是强项**：`MatchReport.strengths` 里混着「技能覆盖」
「证据充分度」这类与研究方向无关的通用条目，两份输入都会拿到同样条数，
拿它比较是恒真的假指标。真正随交集变化的是 `gaps`——没有交集时会多出
「未覆盖：XXX」。

```powershell
# 跑一遍离线指标（不需要 Key、不联网）
.\.venv\Scripts\python.exe scripts\run_all_evals.py

# 存基线；之后 --compare 会逐项报出变化，回归时退出码 1（可直接挂 CI）
.\.venv\Scripts\python.exe scripts\run_all_evals.py --save-baseline
.\.venv\Scripts\python.exe scripts\run_all_evals.py --compare
```

**缺 Key 时是跳过并说明原因，不是整轮失败**——需要真实模型的评测会标成
`llm.disambig: 未配置 LLM_API_KEY…`，其余指标照常跑完。这与
`CLAUDE.md` 的「默认主干必须免费免 Key」一致。

另有两个专项脚本：
- `scripts/run_disambiguation_evals.py`：只看消歧，可 `--rule` 跑规则基线对比；
- `scripts/verify_features.py`：把各阶段新增能力逐项跑一遍，输出中文结果。

数据：`evals/disambiguation_golden.jsonl`（11 位导师）、`evals/gold_claims.jsonl`。
测试：**54 个测试文件 / 543 条用例**，覆盖 Harness 契约、预算闸门、轨迹、
工具契约、消歧、证据校验、匹配、评测自身、离线流程、界面。

## 现在的边界与下一步

**已经立得住的**：Model / Prompt / Tool / Loop / Budget / Trace 六块齐全且可测；
工具契约集中且自校验；轨迹可观测；证据可追溯；无 Key 可降级。

**还缺的**：

1. **Context / State / Workflow 三个抽象还没抽出来**——现在它们散在
   `agents/research.py` 的控制流和 Streamlit session 里。
2. **没有语义召回**：匹配靠可解释的关键词/同义词规则 + LLM 推理，
   embedding 语义召回尚未接入。
3. **没有 HTTP 服务层**：目前只有 Streamlit 前端，Harness 本身与界面无关，
   抽一层 FastAPI 是自然的下一步。
4. **评测还不成体系**：有两个金标集，但缺"一键跑全指标 + 看板"。

这三件事是通往"可复用 Agent Harness"的主要距离，也是下一阶段的重点。
